# Phase 1 progress

Phase 1's agreed in-process acceptance scope is complete: **79 tests pass on native Java 17**, and the expanded original-revision single-player comparison passes. See the [acceptance evidence and limits](phase1-acceptance.md). The [project plan](../../docs/superpowers/plans/2026-09-30-multiplayer.md) remains the roadmap; Phase 2 orders/private views comes next.

## Implemented seams

The following records the extraction in implementation order; later entries supersede earlier temporary limitations. The consolidated acceptance section below describes the current coverage.

- `PlayerSeat` and `ControllerRegistry` provide persisted empire ownership. `Empire.isAIControlled()` uses that roster when installed; old single-player saves continue to use the existing local-player rule.
- `Empire.isHumanEmpire()` separates rule eligibility from the empire shown by the local UI. Colony production, waste, starting challenge resources, troop limits, research restrictions, and war permissions now use human ownership. `GameSession.startGame(options, registry)` can install the roster before galaxy creation, so starting resources use the same rule.
- `TurnCoordinator` records the ordered phases of the desktop turn. `GameSession.nextTurnProcess()` runs its existing operations in those phases without reordering notification points.
- Galactic Council convention fields are serialized. `DecisionRouter` describes the next human vote with a stable owner and decision ID, and rejects stale, wrong-owner, and illegal replies. The existing desktop vote call remains available.
- `CouncilDecisionAdapter` separates convention presentation from Council rules. The default desktop adapter opens the existing panel. `InProcessCouncilDecisionAdapter` accepts separate seat providers, advances AI votes, and routes each human vote through `DecisionRouter` in the existing voting order.
- Research selection now records a pending sequence on `TechCategory`. `ResearchDecisionRouter` validates the owning seat and legal technology, and `ResearchDecisionAdapter` preserves the desktop panel while allowing separate in-process providers. All four scientist variants that request human research choices use this route.
- Turn notifications now live in the current `GameSession` instead of a process-global list. `TurnNotificationSink` preserves desktop delivery by default; `StrictInProcessNotificationSink` handles the extracted research choice and fails when an unadapted notification would open a UI panel.
- Queued turn notifications now carry an optional recipient empire. Research selections name their owning empire, and the in-process sink checks that owner before delivery. With a controller roster installed, the desktop sink refuses unknown or nonlocal recipients instead of displaying their notices to the local viewer. Other notice producers still need recipient tagging and adapters.
- Notification delivery now leaves the queue intact when a sink rejects a batch, and a retry does not add a second systems-scouted notice. Further `isPlayer()` rule auditing moved governor spending, leader overthrow protection, ship design fallback, spy tech restrictions and spending, troop limits, and one tech roll to human ownership.
- `TurnCheckpoint` exposes a completed-phase cursor and the currently recoverable Council and research decisions from serialized model state. It refuses snapshots taken inside an active phase. This is a server-side snapshot of model state, not yet a crash-safe checkpoint or a method to restart the desktop turn loop.
- Turn preparation now transfers each human empire's budget, and the end-of-turn governor pass runs for each human empire. Visibility refreshes and scout updates also run for each human empire, rather than only for the local viewer.
- A rostered match now resolves ship and ground battles automatically, without opening the local tactical panel for either human participant. The existing single-player combat setting remains on its prior path.
- Colonization notifications now identify the fleet's empire. A separate in-process provider can accept or decline colonization for that seat; the desktop adapter keeps the existing panel. The provider still answers synchronously, and colony ship choices are not yet persisted decision barriers.
- Allocation prompts now live in the session under their owning empire. Colony capture names the conquering empire before the system owner changes; the desktop popup reads only the local empire's requests. Alerts also live in the session with recipient IDs for sabotage, transports, trade, spying, trespassing, and alliance standing. Unknown-recipient alerts are rejected in rostered matches.
- `MatchOutcomeEvaluator` derives a result for each human seat and a whole-match finish state for sole-survivor military victories, settled Council rulings, and matches with no surviving humans. The rostered turn loop uses that whole-match state, so losing the local viewing empire alone does not end another human's campaign. The existing `GameStatus` still serves the single-player route.
- Council voting now has a separate named turn phase. A deferred adapter can leave the convention at a completed phase boundary with an owner-specific vote pending; `TurnCheckpoint` also reports owner-specific accept-or-defy ruling decisions. In-process providers can answer both decision types, and duplicate or wrong-owner replies are rejected. Council final-war outcomes in rostered matches use coalition membership rather than the local player's `GameStatus`; vote-order options apply to all human voters. `TurnCoordinator` rejects starting another turn while its prior phase sequence is incomplete.
- Scouted-system lists now belong to each human empire instead of a process-global collection. Scout events identify the viewing empire, and the in-process notification sink can deliver system IDs to that seat's provider. The local desktop popup still reads its own empire's list.
- Technology discovery, plunder, trade, and the existing debug espionage notice now name the acquiring empire as recipient.
- `GameSession.advanceInProcessTurn()` can run rostered phase work with a strict notification sink, return at an owned Council vote or ruling, and resume at the next phase after the response. It keeps notification processing inside the phase that produced it, so a rejected notice cannot silently advance the cursor. Read-only discovery, plunder, and trade technology results now reach a seat-specific in-process provider as data. Governor calculations skip desktop research widgets in rostered games.
- Espionage technology and optional framing choices now pass through `EspionageDecisionAdapter`. The desktop adapter preserves the existing panel; the in-process adapter validates the chosen technology and framing empire against a seat-specific choice record. Its provider still responds synchronously and has no persisted decision barrier.
- Constructed ship counts now belong to the producing empire in session state. The desktop popup reads only its local empire, and the strict in-process sink delivers design IDs and counts to that empire's provider.
- Diplomacy notifications created from an `EmpireView` now carry the view's recipient empire, including formerly immediate war declarations. A constructor without a recipient fails in rostered games. The strict in-process sink handles trade, peace, pact, alliance, and joint-war offers for that seat with the same model actions as the desktop buttons. Other diplomatic messages are delivered as information. An optional mode defers offers in memory; they still lack a guarded save/reload barrier.
- Local-perspective advisor and GNN news panels are suppressed in rostered matches until their content can be built for each viewer. Their gameplay producers still run, including ranking's random draw; ordinary single-player presentation stays on the existing route.
- The in-process notification path removes each successfully delivered notice before handling the next one. If a later provider rejects a notice, a retry will not replay prior choices from the same batch. The desktop path retains its existing batch presentation.
- In-process notification delivery now has its own recorded post-phase step. A provider rejection leaves model work completed and delivery pending, so attaching a provider and calling `advanceInProcessTurn()` again does not repeat production, combat, or diplomacy. Fleet launch is a separate phase after preparation notices for the same reason. `TurnCheckpoint` refuses a phase with pending delivery.
- An optional deferred-research sink consumes owned research notices without presenting a desktop panel. The in-process driver returns the persisted research choices at the next completed phase boundary and resumes after `ResearchDecisionRouter` receives the replies. Other supported notices in that delivery step are consumed first. A research choice left at the final phase also holds the completed turn cursor until answered.
- A second strict sink mode defers colonization as an owner-specific choice. The completed phase cursor stops until the matching player answers. Acceptance rechecks colony eligibility; repeated or wrong-owner replies do nothing. The existing synchronous desktop path remains available.
- A `deferredDecisions` sink also queues diplomatic offers for an owned accept/refuse reply. The offer amount and target are captured when the notice is delivered. Information messages still go to that seat's provider. Both deferred and synchronous replies use one model action path. Notices created by a reply are delivered before the next model phase.
- Checkpoints reject outstanding turn notifications. Council now has a post-phase delivery step before its vote checkpoint, matching the other phase boundaries.
- Rostered bombardment now uses a synchronous owner-specific attack choice instead of opening `RotPUI`. It applies full or target bombardment in the invasion phase, then queues a recipient-tagged result with before/after colony values for each affected human seat. Missing result providers can be attached and retried without repeating the attack. The desktop branch still opens its existing panels.
- Rostered sabotage missions now use a synchronous owner-specific provider for a legal action and target system or cancellation. The outcome is queued for that owner and delivered after invasion work, so a missing result provider does not repeat sabotage. Sabotage incident names now come from the victim's system view instead of the global local viewer.
- Rostered alerts now become serialized `AlertRecord` values at creation, with a recipient, type, formatted description, and system ID. Alert classes that used `player()` to select a system name or message branch now format for the recipient. The desktop path still uses `GameAlert` objects. `GameSession.alertRecordsForEmpire` exposes only one empire's records, and decision-barrier saves no longer lose rostered alerts.
- Initial ship design choices and post-load spy validation now apply to each human empire. Rostered extinction and alliance events leave the legacy single-player `GameStatus` untouched; the match outcome evaluator owns those results.
- Automatic system flagging and automated combat confidence now use each human empire's ownership, while local map-centering and ship-style choices remain viewer settings. Colony-orbit checks skip a fleet's own empire by identity. The rostered outcome evaluator now ends a match when an active human is allied with every surviving empire and records a shared military-alliance result. The "No Alliances" option disables this result, including the desktop sign-alliance path.
- Missile-base maintenance now uses the colony owner's technology cost. Budget cleaning diagnostics and system alert checks read the empire whose state they inspect; ship design names and the attacked-system list also use their owning empire rather than the local viewer.
- Galaxy startup now prepares each rostered human empire and leaves initial notifications queued for the strict in-process sink. `InProcessMatchDriver` drives one turn across the recoverable decision barriers with a separate provider for every human seat. A stolen-technology result with a completed mission is delivered as an owned technology notice.
- Roster ownership, rather than the global autoplay setting, now determines which empires are AI controlled. Dynamic difficulty in a rostered game uses the strongest surviving human empire as its reference, so the local viewing empire cannot change AI scaling. A roster naming a nonexistent empire is rejected at game start.
- Human system views now receive the initial forward-rally setting regardless of which empire the desktop views. Rostered rebellion processing skips the local-view-only news formatting after applying rebellion rules.
- The normal JAR accepts a `phase1` console argument for a tiny in-process exercise with two human seats and one AI empire. `turn` advances through owner-tagged console decision providers; `status` reports the match outcome. The full JAR packages with media conversion skipped. This launcher has no strategic-order editor or remote client.
- `saveDecisionBarrier`/`restoreDecisionBarrier` use the existing atomic local save writer for a completed phase with a pending Council, research, colonization, or diplomatic reply. Saving refuses transient notifications or alerts and checks colony fleet and design identity. Rostered alerts are now serializable records, so they do not trigger that transient-alert guard. Restore compares the exact pending checkpoint, rebinds the session, and restores the simulation RNG; callers must reattach transient providers. The older Council-only entry points remain. Real save/reload scenarios now run in `InProcessRecoveryTest`; see the validation results below.
- `saveInProcessCheckpoint`/`restoreInProcessCheckpoint` extend the same guarded path to any completed phase boundary, including those without a pending decision. Restored phase cursors resume at the next model phase; active model work and undelivered transient notices remain invalid save points.
- `advanceInProcessPhase()` stops after one named model phase and its notification delivery, making intermediate guarded checkpoints reachable by a caller.
- `InProcessMatchDriver` can observe every completed phase before continuing, allowing a caller to save before invasion work. End-of-turn reply notices are drained without inadvertently starting another turn.
- The legacy desktop `nextTurn()` entry point now rejects rostered sessions, preventing a second turn thread from bypassing the in-process phase cursor.
- Rostered alerts directed at valid, unassigned AI empires are discarded; invalid empire IDs are rejected. This matches the controller registry rule that an unassigned empire is AI controlled.
- Rostered ship combat no longer inserts the local viewing empire into results for a battle involving only another human. Automatic combat's harmless-colony targeting setting now applies to the actual human attacker.
- Deferred diplomatic replies recheck contact, survival, treaty state, trade capacity, and joint-war target state before applying. An offer made stale by an earlier reply is consumed without creating an invalid treaty or war.

## Consolidated acceptance (October 1)

The [acceptance ledger](phase1-acceptance.md) records the complete coverage matrix, review findings, fixes and final verification evidence.

- The suite has 79 cases: 72 real-engine recovery/ownership/outcome cases plus seven registry, phase coordinator and RNG unit cases. Router rejection tests live in `InProcessRecoveryTest`, where they exercise actual pending decisions and model effects.
- Recovery includes partially answered research and Council rulings, five-turn continuation, every supported barrier, missing-provider delivery retry, and pending production/assessment work. Each restored fixture is compared with uninterrupted execution using selected gameplay state and RNG continuation.
- Diplomacy covers all five supported offer families with acceptance, refusal, stale choices and save/reload. Recipient coverage includes scouts, technology, construction, combat, bombardment, espionage, sabotage and alerts for both humans.
- Outcome coverage includes military and alliance victory, No Alliances, elimination of the viewing empire, elimination of every human while AIs survive, peaceful Council rules and completed final-war coalitions. Realms Beyond also disables alliance victories, including for a defying prior ally.
- Reproduced defects were corrected in AI bombardment, peaceful Council winners, player automation selection for the second human, pending colony/empire/research state, ship-production estimates and persistent RNG restoration. The earlier lost tax-spending flag regression remains covered.
- The original-revision single-player probe now compares ordinary turns, research completion and its next choice, colonization, automatic combat, diplomacy, military victory and a separate Council victory, including subsequent RNG values. It uses separate JVMs and an original-source overlay, not a second checkout.
- Native Java 17 replaces the earlier Java 26-only validation. The portable JDK is under `target/phase1-tools`; system Java is unchanged. The acceptance profile isolates test classes and uses a 180-second test-process limit. Settings and saves are temporary, animations are disabled, and Swing remains hidden.
- One final review found four important issues, all addressed with regressions. The earlier two-turn console smoke test remains useful supplemental evidence, not the acceptance gate.

Final pass/fail evidence is recorded in the acceptance ledger. This is bounded in-process validation, not a proof over every game state or every serialized field.

## Scope limits for later phases

- Only completed, fully delivered model phases are guarded save points. A provider failure inside active model work requires restoring a prior checkpoint; the partial in-memory phase cannot resume. Bombardment, espionage, and sabotage currently require synchronous owner-specific responses inside the invasion phase.
- The strict sink rejects unexpected desktop notices. Rostered games omit advisor and GNN presentation. The notification queue remains transient because UI notification objects are not a save format. Typed, private, localizable client events and views belong to Phase 2.
- Allocation prompts still use legacy UI text, and the desktop loop does not resume from `TurnCheckpoint`. Direct strategic orders, remote clients, and headless startup are outside Phase 1. No LAN match is playable yet.
